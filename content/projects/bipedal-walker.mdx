> **Status: in progress.** The CAD-to-simulation pipeline and the digital-twin validation are done. No walking controller is deployed yet. The work below checks that the simulator can be trusted first.

The robot has six joints driven by ST3215 servos, with a Jetson Orin Nano on the torso. A single command regenerates the simulation model from CAD.

The interesting part isn't the pipeline. It's what happened when I stopped building the controller and asked whether the simulator deserved to be trusted.

## The question

I didn't want to write a controller and debug it against a simulator of unknown quality. So I ran a validation phase first. It had one deliverable: **can this digital twin predict the real robot well enough to design a controller against?**

## The finding: a missing physical term

The actuator model could not stabilize the robot. It was **3.3× too slow**. Its bandwidth was 4.4 rad/s, against unstable modes up to 14.4 rad/s. The robot was uncontrollable in simulation before any controller existed.

![Instability rate at each pose against actuator bandwidth. The shipped actuator (4.4 rad/s) sits below almost every mode it has to suppress. The corrected model clears all of them.](/projects/biped-bandwidth-margin.png)

The reflex is to tune gains. That would have been wrong. A DC motor's torque-speed line implies a back-EMF damping of **0.624 N·m·s/rad**. The model used **0.05**, which is 12.5× too small.

Because that damping was missing, a control gain had been quietly fitted to do its job. So the model passed every check that didn't test bandwidth directly. Mass, inertia, center of mass, contact, friction and kinematics all looked fine. One parameter was standing in for another, and no single-subsystem test could see it.

With the correct damping, the speed limit falls out of physics: 4.00 rad/s, inside the datasheet's 4.712. Of 30 candidate parameter sets that pass the search, **every one uses the physical damping value**.

**The lesson:** this only showed up by cross-checking two independent analyses. System identification says what the datasheet allows. Modal analysis says what stabilizing the robot requires. Each was consistent on its own. The contradiction sat between them.

## Three more things the validation caught

**One pose is not the robot.** Earlier work looked only at standing. Across 12 poses from a gait, the worst case needs **1.86×** more bandwidth than standing. A walking gait passes through every one of them.

**An assumption was carrying most of the dynamics.** Joint armature was set to 0.01. That value supplied 86 to 99% of total joint inertia, yet it wasn't derived from anything. It is now set from a verified gear ratio. The habit it taught: check which parameters are both important and unverified.

**The biggest error source wasn't the obvious one.** I expected contact switching to dominate the linear model's error. It was **Coulomb friction**. Zeroing it cut the error by four orders of magnitude.

## The reward curve lied

In parallel I trained a walking policy with RL. The training curves looked healthy. Measured on physical metrics, it failed.

- Duty factor was 1.00 and 0.98. Both feet stayed planted almost all the time.
- It was commanded 0.30 m/s and moved at 0.002 m/s.
- It "survived" each episode by standing still, which the reward allowed.

The policy found the easy answer, which was not falling, without doing the task. It's the same lesson as in [my RL work](/projects/deep-rl-cs285): a reward curve can hide what the robot is actually doing.

## Status

Mass, inertia, center of mass, contact, friction and kinematics are validated. The actuator itself has not been measured on hardware yet, so every conclusion above still depends on a datasheet.
